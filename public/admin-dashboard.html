    How filters work

    1. Enter one case-insensitive literal pattern per line.
    2. Choose an input action and, when needed, output masking.
    3. Select global or model scope, review the rule, and then activate it.

    Actions

    Block rejects matching input with HTTP 400.

    Mask replaces matching text with [FILTERED].

    None leaves that direction unchanged.

    Masking example

    Pattern: employee@example.test

    Before: Contact employee@example.test

    After: Contact [FILTERED]

    Input block example

    Policy name: Example input policy

    Literal pattern: sample@example.test

    HTTP 400 { "error": "Request content was filtered", "code": "content_filtered", "filter_name": "Example input policy" }

    An active non-global filter with no selected models does not take effect. Filtering uses literal matching only for documented chat text fields; it is not a general DLP tool.

    Patterns are literal substrings, not regular expressions. They are stored in plaintext in SQLite and backups. New filters are inactive by default. Global scope ignores model selection.
